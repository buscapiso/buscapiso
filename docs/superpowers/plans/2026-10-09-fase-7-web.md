# Fase 7: buscapiso en el navegador. Plan de implementación

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** La web de buscapiso funciona sin servidor en GitHub Pages, con el motor en TypeScript, datos en IndexedDB, exportar/importar, y una extensión MV3 que lee los portales.

**Architecture:** `web/src/engine/` (puro, sin DOM de página ni IndexedDB) + `web/src/store/` (IndexedDB) + `web/src/lib/api.ts` como fachada con las firmas de hoy. `extension/` es un fetcher genérico (fetch y, si hay captcha, pestaña) al que la web habla por un content script puente.

**Tech Stack:** Svelte 5, TypeScript 5.9, Vite 8, Vitest 5 (jsdom), zod, fake-indexeddb (dev), Playwright (e2e con `--load-extension`).

**Spec:** `docs/specs/2026-10-09-web-extension-diseno.md`

Plan compacto por petición expresa (ahorrar tokens): cada tarea fija ficheros, interfaces y qué prueban los tests; el código se escribe en la propia tarea, con TDD.

## Hallazgos de la prueba de viabilidad (2026-10-09)

Chromium con la extensión mínima, perfil limpio, ventana visible:
- Fotocasa (pisos), Habitaclia, Roomgo y De Piso en Piso: `fetch()` desde la extensión responde 200 con la página completa. Sin pestañas.
- Fotocasa habitaciones: la URL `compartir/pisos/barcelona-capital/l` da 404 (con página de 430 KB); revisar la zona al portar.
- Idealista: `fetch()` da 403 (captcha de DataDome). En pestaña sale el captcha; la primera vez nadie lo resolvió y venció el plazo, la segunda lo resolvió la usuaria y la página llegó entera (504 KB). Resolver el captcha es el camino normal de Idealista, no la excepción: el aviso `needs-user` tiene que ser claro y verse bien, y tras resolverlo se reintenta `fetch()` (con la cookie nueva puede bastar) antes de seguir en pestaña. Con el navegador marcado como automatizado no pasa nunca: en el e2e no se usa Idealista real.
- Conclusión: el diseño de la spec vale tal cual (fetch, y pestaña con espera y `needs-user`).

## Global Constraints

- Origen de la web: `https://buscapiso.github.io`; ruta `/buscapiso/`; Vite `base: '/buscapiso/'`.
- Protocolo de la extensión: `protocol: 1`, mensajes `hello`, `fetch`, `result`, `progress`, `cancel` exactamente como en la spec.
- Hosts de la extensión: `*.idealista.com`, `*.fotocasa.es`, `*.habitaclia.com`, `*.roomgo.es`, `*.depisoenpiso.com`; `localhost` solo en la compilación de desarrollo.
- Id de anuncio: `sha1("portal:sourceId")`, 12 hex.
- Export: `format: "buscapiso"`, `version: 1`, `kind: share|backup`, máximo 50 MB, nunca claves.
- Pausa por portal 3 a 8 s (el rango de cada fuente de Python); portales en paralelo.
- Nombres del motor en inglés. Textos de UI en `web/src/lib/locales/en.json`.
- Texto de portales e importaciones nunca con `{@html}`; URLs solo `http(s)`.

## Review Focus

1. Importar un fichero con anuncios que ya tienen nota local: la nota no cambia (test en Tarea 5).
2. Captcha que nadie resuelve: a los 180 s ese portal falla con `timeout`, los demás siguen y la búsqueda termina (test en Tarea 6).
3. Dos pestañas de buscapiso abiertas con búsqueda programada: solo una busca (test en Tarea 4, Web Lock).
4. Transitous caído: los trayectos salen como estimación en línea recta y la búsqueda no falla (test en Tarea 3c).
5. Mensaje `postMessage` de otro origen o URL fuera de los portales: la extensión lo ignora o responde `not-allowed` (test en Tarea 6).

### Task 3: Motor en TypeScript

Una subtarea por bloque; cada una con test rojo → código → verde → commit.

**3a. Modelo y base** — `engine/model.ts` (`RawListing`, `Derived`, `UserState`, `listingId(source, sourceId): Promise<string>`, `totalCost`, `estimatedCost`), `engine/sources/base.ts` (`inferGender`, `surface`). Tests: id coincide con Python para 3 casos; inferencia de género con las frases de `test_genero.py`.

**3b. Fuentes** — `engine/sources/{idealista,fotocasa,habitaclia,roomgo,depisoenpiso}.ts`, interfaz común:
```ts
export interface Source {
  name: string; types: ListingType[]; pause: [number, number];
  blockedMarkers: string[]; readyMarkers?: string[];
  listUrls(area: Area, profile: Profile, page: number): string | null;
  parseList(html: string): RawListing[]; totalPages?(html: string): number;
  detailUrl?(l: RawListing): string; parseDetail?(html: string): Partial<RawListing>;
}
```
Tests: cada parser contra su dorado, campo a campo; URLs iguales a las de `test_*.py`.

**3c. Trayectos y geocodificación** — `engine/travel.ts` (`TravelProvider.trips(origins, dest)`; Transitous `one-to-all`/`plan`, Google matrix, MOTIS; caché vía interfaz `TravelCache`; fallback línea recta con `source:'estimate'`), `engine/geocode.ts` (Nominatim 1/s, caché, centroide de barrio). Tests: con las fixtures `transitous_*.json`; Transitous lanza → estimación.

**3d. Dedupe, ranking, perfiles, cobertura** — `engine/dedupe.ts`, `engine/ranking.ts`, `engine/profiles.ts` (zod; mismos defaults que `profiles.py`), `engine/coverage.ts` + `engine/data/zonas.json`. Tests: dorados de ranking; casos de `test_deduplicar.py`, `test_profiles.py`, `test_cobertura.py`.

**3e. IA y avisos** — `engine/ai/{providers,extract}.ts`, `engine/notify.ts`. Tests: con `fetch` falso, cabeceras y cuerpo por proveedor; caché.

**3f. Pipeline** — `engine/pipeline.ts`: `runSearch(deps, profile, opts, emit): Promise<Summary>` con `deps = {fetchPage, store, travel, geocode, ai?, notify?, now, sleep}`. Tests: fetcher falso con fixtures; un portal bloqueado no tumba a los demás; cancelar; eventos `SearchEvent`.
