# Buscapiso v2: plan para convertirlo en una app compartible

Fecha: 2026-10-08

## Objetivo

Pasar del script de terminal actual a una aplicación que otra persona pueda
instalar y usar sin tocar código: interfaz en inglés, ajustes elegidos antes de
cada búsqueda, seguimiento de cada anuncio y funciones de IA con la clave de
cada usuario. Debe poder consultarse desde un iPhone o un iPad.

Alcance de esta versión: Barcelona y su área metropolitana, habitaciones y
pisos enteros.

## Punto de partida

Lo que ya existe y se reutiliza casi entero:

| Pieza | Fichero | Qué hace |
|---|---|---|
| Fuentes | `fuentes/*.py` | Idealista, Fotocasa, Roomgo y De Piso en Piso, con recuperación ante bloqueo |
| Navegador | `navegador.py` | Playwright con ventana visible (headless lo bloquea DataDome) |
| Trayectos | `transporte.py`, `datos/red.json` | Dijkstra sobre 116 estaciones, error de ±4 min |
| Zonas | `cobertura.py`, `datos/zonas.json` | elige qué zonas rastrear según el tiempo máximo |
| Ranking | `ranking.py` | filtros duros y puntuación con los pesos de `config.yaml` |
| Histórico | `almacen.py`, `pisos.db` | SQLite con novedades y estados |
| Tests | `tests/` | sin red, contra HTML real guardado |

Tres hechos del código actual condicionan el diseño:

1. El programa no usa ninguna IA. El género del piso, las visitas y el alquiler
   de temporada se detectan con expresiones regulares. La IA será una función
   nueva y opcional, y las regex se quedan como respaldo para quien no ponga
   clave.
2. El rastreo necesita un Chromium visible en un ordenador con conexión
   doméstica. Un servidor en la nube rastreando para todos los usuarios
   recibiría captchas de DataDome desde el primer día (las IP de centro de
   datos están marcadas) y concentraría el riesgo legal en una sola persona.
   Por eso el rastreo se queda en el ordenador de cada usuario.
3. Un iPhone no puede ejecutar Playwright. La app del móvil tiene que ser una
   ventana a un motor que corre en otro sitio.

## Arquitectura propuesta

```
 Ordenador del usuario (Windows / Mac / Linux)
 ┌───────────────────────────────────────────────────┐
 │  Motor (Python)                                   │
 │   fuentes + navegador + trayectos + ranking       │
 │   programador de búsquedas                        │
 │   adaptador de IA (clave del usuario)             │
 │   SQLite                                          │
 │            │                                      │
 │   API local (FastAPI)  ──  sirve la web app       │
 └────────────┬──────────────────────────────────────┘
              │ http://localhost  /  red local  /  Tailscale
     ┌────────┴─────────┐
     │  Web app (PWA)   │  navegador del ordenador, iPhone, iPad
     └──────────────────┘
```

El motor es el código actual reorganizado como librería, con una API HTTP
encima. La interfaz es una web app instalable (PWA) que el mismo motor sirve.
En el ordenador se abre sola en el navegador; en el móvil se abre escaneando un
QR que muestra la app y se añade a la pantalla de inicio.

Para usarla desde el móvil fuera de casa hay dos caminos:

- Tailscale (gratis, se instala en el ordenador y en el móvil). No requiere
  abrir puertos ni montar nada en la nube. Es la opción que recomiendo para la
  v2.
- Una sincronización opcional con una base de datos en la nube (Supabase o
  similar), que dejaría ver y marcar anuncios con el ordenador apagado. Añade
  cuentas de usuario y un servicio que mantener, así que la dejo para después.

Tecnología:

| Capa | Elección | Motivo |
|---|---|---|
| API | FastAPI | Python como el resto; tipado con Pydantic |
| Interfaz | SvelteKit o React + Vite, compilada a estáticos | PWA, funciona en Safari de iOS |
| Mapa | Leaflet + teselas de OpenStreetMap | gratis, sin clave |
| Base de datos | SQLite (la actual, migrada) | un fichero, sin servidor |
| Empaquetado | PyInstaller + GitHub Actions | un instalable por sistema operativo |
| Chromium | descarga en el primer arranque (`playwright install chromium`) | evita un instalador de 150 MB |

## Requisitos

### 1. Interfaz nueva

Pantallas:

- Onboarding: idioma, primer perfil de búsqueda, clave de IA (opcional),
  prueba de que el navegador arranca.
- Resultados: lista de tarjetas con foto, precio total, tiempo a cada destino,
  puntuación y motivos ("+25 publicado hoy", "-12 gastos sin declarar"), con
  filtros y orden. Un botón alterna lista y mapa.
- Mapa: pisos coloreados por puntuación, destinos del usuario marcados, zonas
  rastreadas sombreadas.
- Ficha: fotos, descripción, datos extraídos, trayectos, historial de precio,
  estado, notas y enlace al anuncio original.
- Tablero de seguimiento (ver punto 6).
- Ajustes y perfiles de búsqueda (punto 3).
- Progreso de la búsqueda en vivo: qué portal, cuántos anuncios, captchas
  pendientes. Hoy esto son `print` en la terminal.

Diseño pensado primero para móvil: tarjetas a una columna, gestos para marcar
me gusta o descartar, y la tabla densa solo en pantallas anchas.

### 2. Inglés

- Toda la interfaz con cadenas en ficheros de traducción (inglés por defecto,
  español y catalán como segundo paso, casi gratis una vez montado).
- README, instrucciones de instalación y mensajes de error en inglés.
- El código pasa a inglés a medida que se toca cada módulo. Los parsers siguen
  entendiendo español y catalán, porque los anuncios están en esos idiomas.

### 3. Ajustes antes de buscar

Los ajustes viven en perfiles de búsqueda guardados en la base de datos y se
editan desde la app; `config.yaml` y `zonas.yaml` desaparecen como interfaz de
usuario. Cada búsqueda empieza con el perfil activo y se puede retocar antes de
lanzarla.

| Grupo | Ajustes |
|---|---|
| Tipo | habitación / piso entero |
| Dónde | portales a usar; zonas incluidas y excluidas dibujadas o elegidas en el mapa; o "lo que quede a menos de N min de mis destinos" (lo que ya hace `cobertura.py`) |
| Destinos | lista libre de sitios (trabajo, universidad, pareja...) elegidos en el mapa o por dirección, cada uno con tiempo máximo e importancia |
| Dinero | presupuesto ideal y máximo (alquiler + gastos), gastos supuestos si no se declaran, fianza máxima |
| Convivencia (habitación) | género del piso (solo chicas / solo chicos / mixto / me da igual), propietario en casa, número de compañeros, rango de edad, parejas, visitas, mascotas, fumadores |
| Piso entero | habitaciones, metros, ascensor, amueblado, exterior |
| Fechas | entrada a partir de, estancia mínima, excluir alquiler de temporada |
| Preferencias | importancia de novedad, precio, trayecto, etc. con tres niveles (poco / normal / mucho); los pesos numéricos actuales quedan en un modo avanzado |

Hay que generalizar dos cosas del código:

- `transporte.py` recibe destinos con nombre de estación (`Fira`,
  `Collblanc`). Pasa a aceptar coordenadas: el grafo ya calcula el tramo a pie
  hasta la estación más cercana, así que cualquier punto de Barcelona sirve
  como destino.
- `requisitos.solo_chicas` pasa a ser un campo de género con cuatro valores.
  La lógica de "género sin confirmar, pregunta tú" se mantiene para cualquier
  valor.

### 4. IA con la clave de cada usuario

Funciones (todas opcionales; sin clave la app funciona como hoy):

| Función | Qué hace |
|---|---|
| Extracción | lee la descripción y devuelve JSON: género del piso, gastos incluidos, normas, temporada, edad y ocupación de compañeros, fecha de entrada. Sustituye a las regex cuando hay clave y entiende catalán o inglés sin reglas nuevas |
| Resumen | una frase por anuncio y una lista corta de pros y contras según el perfil del usuario |
| Alertas | señales de fraude (precio muy bajo, pide pagar antes de visitar, texto copiado de otro anuncio), temporada encubierta, anuncio viejo resubido |
| Mensajes | borrador del primer mensaje al anunciante en su idioma, con los datos del usuario y las preguntas que faltan (por ejemplo, si el piso es solo de chicas) |
| Ajustes por texto | el usuario describe lo que busca y la IA propone el perfil, que él revisa antes de guardar |

Proveedores, detrás de un adaptador común:

- Anthropic (Claude), con clave de API.
- Google Gemini, con clave de AI Studio. Tiene un nivel gratuito con límites
  de uso, así que lo pondría como opción recomendada para quien no quiera
  pagar.
- Cualquier API compatible con OpenAI: OpenAI, OpenRouter, y modelos locales
  con Ollama (gratis y privado, pero necesita un ordenador potente).

Sobre la suscripción de Claude: una suscripción Pro o Max no se puede usar
desde aplicaciones de terceros; las condiciones de Anthropic lo reservan para
sus propias apps y Claude Code. Para esta app cada usuario necesita una clave
de API, que se paga por uso y aparte de la suscripción. Conviene comprobar las
condiciones vigentes antes de publicar.

Control de coste:

- La extracción se hace una vez por anuncio y se guarda junto a un hash del
  texto; si el anuncio no cambia, no se vuelve a pagar.
- Solo se procesan los anuncios que pasan los filtros duros baratos (precio,
  zona, trayecto).
- La app muestra el número de llamadas y una estimación de gasto por búsqueda,
  con un tope configurable.
- Modelo pequeño por defecto (Haiku, Gemini Flash o similar).

La clave se guarda en el llavero del sistema operativo (librería `keyring`),
nunca en texto plano ni en la base de datos.

Instrucciones para el usuario, que irán en la app y en el README:

1. Gemini (gratis para empezar): entrar en aistudio.google.com con una cuenta
   de Google, pulsar "Get API key", crear la clave y pegarla en
   Settings → AI provider → Gemini.
2. Claude: crear cuenta en console.anthropic.com, añadir saldo en Billing,
   crear la clave en API Keys y pegarla en Settings → AI provider → Anthropic.
3. OpenAI u OpenRouter: igual, desde platform.openai.com u openrouter.ai.
4. Ollama: instalar Ollama, ejecutar `ollama pull` con el modelo elegido y
   seleccionar Settings → AI provider → Local (Ollama). No necesita clave.
5. El botón "Test" de esa pantalla hace una llamada mínima y confirma que la
   clave funciona.

### 5. Sin terminal

- Instalables por sistema operativo generados en GitHub Actions: `.exe` o
  instalador para Windows, `.dmg` para Mac y AppImage para Linux.
- Al abrirlo, arranca el motor en segundo plano con un icono en la bandeja del
  sistema (abrir app, buscar ahora, pausar búsquedas programadas, salir) y abre
  la web app en el navegador.
- La ventana de Chromium sigue apareciendo durante el rastreo, porque es lo que
  evita el bloqueo. La app explica por qué en el onboarding y avisa cuando hay
  un captcha esperando.
- La versión de Mac sin firmar obliga a abrirla con clic derecho la primera
  vez. Para un grupo de amigos basta con explicarlo; para público general hace
  falta una cuenta de desarrollador de Apple (99 $/año).

### 6. Seguimiento de anuncios

Estados, en orden:

`new` → `liked` / `hidden` → `contacted` → `visit_scheduled` → `visited` →
`applied` → `got_it` / `rejected`

Además, `discarded` desde cualquier estado, con un motivo opcional.

Cada anuncio guarda:

- estado y fecha de cada cambio (un historial);
- notas libres;
- valoración de 1 a 5;
- fecha y hora de la visita, con exportación a calendario (`.ics`);
- recordatorio de seguimiento ("escribí hace 3 días y no contestan");
- el mensaje enviado, si se redactó con la app.

Vistas: lista filtrada por estado y tablero tipo kanban con una columna por
estado. Exportación a CSV.

El motor detecta cambios entre búsquedas: bajadas de precio, anuncios
retirados (los que estaban en `liked` o `contacted` se marcan como "ya no
publicado") y el mismo piso publicado en otro portal, apoyándose en
`deduplicar.py`.

La tabla de estados actual de `almacen.py` se migra sin perder lo que ya has
marcado.

### 7. Ideas aceptadas

Búsquedas programadas:

- Cada perfil puede rastrearse cada N horas mientras el ordenador esté
  encendido.
- Las notificaciones de anuncios nuevos que superan una puntuación llegan al
  móvil. Opciones: Web Push de la PWA (iOS lo admite desde la versión 16.4 si
  la app está en la pantalla de inicio), un bot de Telegram o ntfy. Telegram es
  lo más fiable de montar; Web Push evita instalar nada más.
- Frecuencia mínima limitada (por ejemplo, 2 horas) para no quemar el perfil
  del navegador con DataDome.

Mapa interactivo: descrito en el punto 1.

Pisos enteros:

- Nuevos parsers para las secciones de alquiler de vivienda de Idealista y
  Fotocasa.
- Habitaclia vuelve a tener sentido: perdió la sección de habitaciones, pero
  sigue publicando pisos enteros.
- El ranking cambia de pesos (no hay compañeros ni género; cuentan más metros,
  habitaciones y estado).

## Fuentes sin rastreo (para más adelante)

De momento la app solo funciona en el ordenador de cada usuario. Estas vías
podrían permitir usarla sin ordenador, y quedan anotadas para revisarlas:

- API oficial de Idealista (developers.idealista.com). El acceso se pide y lo
  conceden a su criterio, sobre todo a profesionales. Hay que comprobar las
  condiciones actuales y si incluye habitaciones.
- Conector de Idealista dentro de Claude. Probado el 2026-10-08: una búsqueda
  de habitaciones en Sants-Montjuïc hasta 550 € devolvió JSON con coordenadas,
  descripción, número de inquilinos, `tenantGender` (`female` / `mixed`) y si se
  permite fumar, con un máximo de 50 resultados por llamada (153 en total para
  esa búsqueda). Solo funciona dentro de una cuenta de Claude con el conector
  activado, no desde una app propia con clave de API. Podría servir para una
  versión de buscapiso que viva dentro de Claude (skill o artifact), que sí
  funciona en el móvil. El campo de género tampoco es fiable del todo: un
  anuncio que dice "solo para chicas" en la descripción venía marcado como
  `mixed`.
- Alertas por email de los portales, reenviadas a la app para que las lea.
- Servicios de terceros que venden resultados de Idealista o Fotocasa. Por
  debajo también rastrean, cobran por resultado y no resuelven la cuestión de
  las condiciones de uso.

Fotocasa, Habitaclia y Badi no tienen API pública, y ningún portal publica
exportaciones masivas.

## Riesgos

| Riesgo | Mitigación |
|---|---|
| Los portales cambian el HTML | tests con HTML guardado (ya existen); la app avisa "Idealista devolvió 0 anuncios, puede haber cambiado" en vez de fallar en silencio; actualizaciones rápidas de la app |
| Bloqueos de DataDome | rastreo desde el ordenador de cada usuario, frecuencia mínima, la escalera de recuperación actual |
| Condiciones de uso de los portales | uso personal y de bajo volumen; no ofrecer un servicio centralizado; no redistribuir anuncios. Antes de publicar el repo abiertamente, revisar las condiciones de cada portal. Idealista tiene una API oficial para socios que podría sustituir al rastreo si concedieran acceso |
| Coste de IA inesperado | caché por anuncio, tope de gasto, modelo pequeño por defecto |
| Claves filtradas | llavero del sistema, nunca en logs ni en exportaciones |
| Datos personales en la nube | en la v2 no hay nube: todo queda en el ordenador del usuario |

## Fases

Cada fase deja algo que funciona.

| Fase | Contenido | Resultado |
|---|---|---|
| 0. Reorganizar | motor como paquete, ajustes en la base de datos en vez de YAML, destinos por coordenadas, género con cuatro valores, migración de `pisos.db`, salida por eventos en vez de `print` | el CLI actual sigue funcionando encima del motor nuevo; tests en verde |
| 1. API y web app | FastAPI, lista, ficha, estados y notas, editor de perfiles, progreso en vivo, en inglés | se usa desde el navegador del ordenador |
| 2. Mapa | Leaflet, destinos y zonas en el mapa, vista mapa de resultados | ajustes de "dónde" visuales |
| 3. IA | adaptador de proveedores, extracción con caché, resúmenes, alertas, borradores de mensaje, pantalla de claves con instrucciones | funciones de IA con la clave de cada uno |
| 4. Móvil y programación | PWA, QR para abrir en el móvil, guía de Tailscale, búsquedas programadas, notificaciones | uso diario desde el iPhone |
| 5. Pisos enteros | parsers de vivienda en Idealista, Fotocasa y Habitaclia, ranking propio | segundo tipo de búsqueda |
| 6. Distribución | PyInstaller, icono de bandeja, onboarding, instaladores en GitHub Actions, README en inglés | un amigo lo instala sin ayuda |
| Después | sincronización en la nube, traducciones, otras ciudades | |

Las fases 0 y 1 son las más largas porque tocan casi todo el código; a partir
de ahí cada fase es independiente y se puede reordenar.
